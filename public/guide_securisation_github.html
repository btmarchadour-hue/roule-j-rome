1. Workflow GitHub & Étanchéité Dev / Production

L’objectif est simple : aucune modification en cours de travail ne doit arriver par surprise sur la version utilisée par Jérôme sur la plage. Tout développement arrive d’abord sur la branche dev, est testé, puis livré consciemment vers la branche de production (main ou principal selon le nom configuré sur votre dépôt GitHub).

Étape A — Mettre dev en branche par défaut (valable pour tous les dépôts)
  1. Ouvrez votre dépôt sur github.com → onglet Settings → menu gauche Branches.
  2. Dans Default branch, cliquez sur l’icône d’échange (Switch to another branch).
  3. Sélectionnez dev (créez-la d’abord depuis la branche de prod si elle n’existe pas encore), puis validez Update.
✓ Résultat : toute synchronisation automatique arrive sur dev et ne touche jamais directement la production.
Étape B — Protéger la branche de production (main ou principal)
  • Si votre dépôt est Public (ou compte GitHub Pro) : dans Settings > Branches > Add branch protection rule, indiquez le nom exact de la branche de prod (main ou principal) et cochez :
    • Require a pull request before merging (interdit tout push direct).
    • Do not allow bypassing the above settings (évite toute erreur de manipulation).
  • Si votre dépôt est Privé sur un compte GitHub Gratuit : les règles de verrouillage automatiques ne sont pas incluses dans l’offre gratuite. Appliquez la discipline équivalente (100 % gratuite et efficace) :
    • Gardez dev en branche par défaut.
    • Livrez toujours vers main / principal via une Pull Request (onglet Pull requests → New pull request → base: prod ← compare: dev) afin de relire la liste des fichiers modifiés avant de fusionner.
    • Créez un Tag / Release daté après chaque livraison stable (ex. v2026.04-prod) pour pouvoir restaurer la version précédente en 2 minutes en cas d’imprévu.

Check-list avant chaque livraison à Jérôme

  • ☐ Build & vérification technique OK : aucune erreur de compilation ni de lint.
  • ☐ Parcours rapide validé : onglet Aujourd’hui (C2), Calendrier (C1), Statistiques, GPS et Clients ouverts sans erreur console.
  • ☐ Zéro secret dans le diff GitHub : vérifier qu’aucun fichier .env ni mot de passe en clair n’apparaît dans la Pull Request.
  • ☐ Base Firestore vérifiée : vérifier que firebase-applet-config.json pointe bien sur la base de Production (et pas sur une base de test !).

2. Secrets, Clés API & Hygiène du Code

Il faut distinguer les secrets véritables (qui ne doivent jamais quitter le serveur ni apparaître dans le dépôt Git) des identifiants publics d’adressage (normaux côté navigateur).

Élément Niveau Où il doit vivre Règle de sécurité
WINDSUP_USERNAME / WINDSUP_PASSWORD Secret serveur Variables d’environnement serveur uniquement (.env local ou hébergeur) Jamais dans le code source, jamais dans Git (.env bloqué par .gitignore). Utilisé uniquement par le relais serveur /api/*.
CANDHIS_API_TOKEN Secret serveur Variables d’environnement serveur Idem : uniquement côté serveur, modèle vide dans .env.example.
Mots de passe équipe (Jérôme, Benoît, Moniteur) Confidentiel Empreintes SHA-256 uniquement (collection app_users) Aucun mot de passe en clair dans le code, les commentaires ou l’interface. Changer le mot de passe d’un compte depuis les réglages Admin met à jour uniquement son empreinte SHA-256.
firebase-applet-config.json (apiKey, projectId, databaseId) Public navigateur Configuration front-end normale Par conception Firebase, cette clé sert à identifier le projet depuis le navigateur. Elle ne protège pas la base : ce sont les règles firestore.rules qui protègent les données.
Audit effectué dans le code : tous les mots de passe en clair, commentaires contenant des mots de passe et anciens codes de secours historiques ont été retirés de l’écran de connexion et des utilitaires d’authentification. La vérification repose exclusivement sur les empreintes SHA-256.

Évolution recommandée avant tout partage élargi : le mode de connexion actuel par profil SHA-256 est idéal pour une équipe restreinte (Jérôme + Benoît) car il fonctionne vite sur smartphone face à la mer sans exiger de compte Google. Toutefois, une authentification purement applicative ne fournit pas de jeton cryptographique au serveur Firestore. Si l’application doit être partagée à d’autres personnes ou exposée largement, il faudra activer Firebase Authentication (Connexion Google) afin que les règles serveur vérifient directement request.auth != null.

4. Sécurité Firebase Firestore & Plan de Sauvegarde

Les règles de sécurité Firestore (firestore.rules) ont été durcies pour remplacer les anciens accès ouverts sans contrôle par des garde-fous structurels vérifiés automatiquement.

Ce que les règles Firestore imposent aujourd’hui

  • Rejet par défaut (Default-Deny) : toute collection non déclarée explicitement est bloquée en lecture et en écriture.
  • Contrôle strict des identifiants de documents : dates au format exact AAAA-MM-JJ sur validations et custom_slots, caractères et longueurs plafonnés (128 car. max) sur toutes les autres collections.
  • Validation des schémas, types et tailles : chaque écriture vérifie les champs obligatoires, leurs types, les bornes géographiques des points GPS (secteur France/Bretagne) et la taille maximale des textes/listes (protection anti-injection et anti-explosion de quota).
  • Protection des réglages & comptes clés :
    • app_config : lecture listée interdite, suppression interdite, écriture limitée aux documents autorisés (session_settings, beach_cadre_roulage) par un auteur admin reconnu.
    • app_users : empreinte SHA-256 (64 caractères hexadécimaux) obligatoire ; suppression et déclassement de usr_jerome et usr_benoit impossibles.
    • team_notes : les 3 documents techniques de suivi (status_tech_notes, qcm_tech_notes, audit_data_c1_c2) ne peuvent pas être supprimés.
    • test/connection : lecture unitaire uniquement (aucune écriture possible).
Point de vigilance à relire avant tout partage : tant que la connexion Google Firebase Auth n’est pas activée sur l’écran de verrouillage, l’URL de l’application doit rester strictement privée entre Benoît et Jérôme (ne pas la publier sur un site public ou un réseau social). Pensez à relire et renforcer les règles Firestore avant d’élargir l’accès.

Routine de sauvegarde (2 minutes, 1 fois par mois en saison)

Même si Firebase réplique automatiquement les données dans le cloud, garder une copie locale protège contre toute fausse manipulation humaine :

  1. Onglet Clients → cliquer Exporter CSV (sauvegarde du répertoire complet).
  2. Onglet GPS / Limite basse → cliquer Exporter CSV (sauvegarde de tous les relevés d’étalonnage plage).
  3. Onglet Statistiques → exporter le bilan de la période en CSV (sauvegarde des séances réalisées / annulées).
  4. Classer ces 3 fichiers dans un dossier daté (ex. Sauvegardes_CaRoule/2026-07/ sur Google Drive ou disque local).

5. Procédure Base de Test Isolée (Zéro risque sur la Prod)

Pour tester de nouvelles fonctionnalités, essayer des imports Excel/CSV ou simuler des saisies de planning sans jamais polluer les vraies données de Jérôme, il faut isoler complètement les tests dans une base Firestore dédiée.

Option recommandée — Créer une 2e base Firestore dédiée (test-lestrevet)
  1. Ouvrez la Console Firebase sur votre projet actuel (genuine-shard-n01dl).
  2. Dans le menu de gauche, allez dans Build → Firestore Database.
  3. Cliquez sur le bouton Créer une base de données (en haut ou via le sélecteur de base existant).
  4. Saisissez l’identifiant : test-lestrevet, choisissez la région Europe (ex. europe-west1 ou eur3) et démarrez en Mode Production.
  5. Une fois créée, ouvrez l’onglet Règles de cette nouvelle base test-lestrevet, copiez-collez le contenu exact de firestore.rules et cliquez sur Publier.
  6. Dans votre environnement de développement / branche dev uniquement, modifiez le champ firestoreDatabaseId dans firebase-applet-config.json pour mettre "test-lestrevet" à la place de l’ID de production.
⚠️ Règle d’or anti-mélange : avant de fusionner dev vers main / principal, vérifiez toujours dans la Pull Request que le fichier firebase-applet-config.json n’a pas été modifié pour pointer vers test-lestrevet ! La production doit toujours conserver son identifiant officiel.
Astuces rapides au quotidien (sans changer de base)
  • Tests GPS sur la plage : utilisez toujours la carte intégrée « 🧪 Tester mon GPS (sans enregistrer) » dans l’onglet GPS — elle mesure la précision et la répétabilité en 2 passages avec zéro écriture en base.
  • Alternative projet séparé : si votre quota de bases par projet est atteint, vous pouvez aussi créer un 2e projet Firebase gratuit (ex. char-a-voile-dev) utilisé uniquement sur une copie locale ou la branche dev.
